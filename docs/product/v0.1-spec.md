# v0.1 Product Specification

## Goal

Prove that Vehicle Intelligence Platform can turn a UK registration or VIN into a trustworthy, explainable Vehicle Passport and use that vehicle context to begin a structured diagnostic session.

## Primary flow

1. User enters a UK registration or 17-character VIN.
2. Input is normalized and validated.
3. Available authoritative/public adapters are queried.
4. Returned observations are stored as evidence, not flattened immediately into unquestioned facts.
5. Resolution produces vehicle assertions with provenance, freshness and confidence.
6. Passport renders identity, official checks and Mechanical DNA.
7. User can report symptoms / DTCs / observations.
8. Diagnostic engine creates competing hypotheses and recommends the safest, cheapest useful next evidence.
9. New evidence updates rather than silently overwrites the diagnostic state.

## v0.1 surfaces

### Lookup
- VRM or VIN input.
- Explain invalid input without pretending a vehicle was found.
- Never expose private keeper information.

### Vehicle Passport
- identity summary;
- VIN/VRM where appropriate;
- evidence freshness;
- confidence/verification state;
- authoritative link-outs;
- Mechanical DNA;
- active diagnostic sessions.

### Official checks
UK-first links include GOV.UK/DVLA/DVSA services for vehicle information, MOT history and recalls. Link-outs remain available even when equivalent data is displayed locally.

### Mechanical DNA
Initial graph categories:
- engine;
- transmission;
- induction/turbo;
- fuel;
- emissions;
- cooling;
- braking;
- suspension;
- electrical.

Unknown components remain UNKNOWN. Candidate component mappings can be shown with evidence and verification prompts.

### Diagnostic session
Input types:
- symptom;
- DTC;
- live-data observation;
- visual inspection;
- sound/behaviour observation;
- installed-part verification;
- repair outcome.

Output:
- ranked hypotheses;
- supporting/contradicting evidence;
- safety severity;
- next discriminating test;
- explanation of why that test is useful;
- confidence changes after evidence is added.

## Reference acceptance scenario

Vehicle #000001: `FG11 YKC` / `W0LPD6EGXBG121817`.

Known user observations for the initial diagnostic fixture:
- fuel is adequate;
- battery issue has been addressed;
- acceleration feels slow;
- turbo/boost airflow sounds more prominent.

The system must not conclude “failed turbo.” It should preserve multiple candidates such as charge-air leak, air metering/EGR, turbo control, fuel delivery and clutch slip, then request discriminating evidence such as DTC/live-data and boost-pipe inspection.

## Explicitly out of scope for v0.1

- paid vehicle-history guarantees;
- finance/write-off/theft claims without a licensed source;
- worldwide coverage;
- proprietary workshop-data scraping;
- automatic parts purchasing;
- ECU coding;
- safety-critical repair instructions sourced only from generative AI;
- pretending VIN characters encode factory options that require an external build database.

## Definition of done

v0.1 is demonstrable when:
1. VRM/VIN inputs have deterministic validation.
2. At least one legitimate UK data adapter or fixture-backed adapter implements the common provider contract.
3. Passport distinguishes CLEAR / UNKNOWN / FLAGGED where relevant.
4. Every material assertion can expose its evidence.
5. Official verification links work.
6. Mechanical DNA supports candidate and verified components.
7. A diagnostic session can ingest evidence and update ranked hypotheses.
8. Vehicle #000001 passes the reference scenario without unsupported certainty.
9. Automated tests cover evidence resolution and UNKNOWN semantics.
10. Documentation names unavailable/licensed integrations honestly rather than presenting roadmap items as live.
